**プロジェクト**: Webシステム開発（システム共通基盤）  
**バージョン**: 1.0.0 → ロールバック先（前バージョンまたは安全な状態）  
**最終更新**: 2026年6月2日

---

## 📋 目的

本番環境で以下のような重大な問題が発生した場合、迅速にロールバックを実施し、サービスを安定した状態に戻すための手順を定義します。

### ロールバックが必要なケース

1. **Critical（重大）なバグが発見された場合**
   - 認証機能の不具合（ログインできない、セキュリティ脆弱性）
   - データ損失・破損の可能性がある場合
   - システム全体が起動しない・応答しない

2. **High（高）な性能問題が発生した場合**
   - API応答時間が目標値（100ms）を大幅に超過（例: 1秒以上）
   - 同時接続数が目標値（10ユーザー）を下回る
   - サーバーリソース（CPU/メモリ）が枯渇

3. **セキュリティ問題が発生した場合**
   - OWASP Top 10の脆弱性が本番環境で悪用された
   - JWT漏洩、セッションハイジャック等の攻撃が確認された
   - 不正なアクセス・データ窃取が検出された

4. **データ整合性問題が発生した場合**
   - ユーザーデータ・セッションデータが破損
   - アプリプラグイン機構が動作しない
   - データファイル（JSON DB）の読み書きに失敗

## ⚠️ ロールバック実施前の確認事項

### 1. 問題の切り分け

- [ ] **問題の再現性を確認**
  - 特定の操作で必ず発生するか
  - 複数のユーザーで発生しているか
  - 環境依存か（本番のみ / ステージングでも発生）

- [ ] **影響範囲の評価**
  - 全ユーザーに影響するか
  - 特定の機能のみか（例: 管理画面のみ、特定アプリのみ）
  - データ損失のリスクはあるか

- [ ] **一時的な回避策で対応可能か**
  - サーバー再起動で解決するか
  - 問題のある機能を無効化すれば継続可能か
  - 設定変更で対応可能か

### 2. ステークホルダーへの連絡

- [ ] **運用チームへ通知**
  - 問題の内容と影響範囲を報告
  - ロールバック実施の意思決定

- [ ] **ユーザーへの事前通知（可能な場合）**
  - サービス停止時間の告知
  - 復旧予定時刻の連絡

### 3. データバックアップの確認

- [ ] **最新のバックアップが存在することを確認**
  - バックアップ日時を確認
  - バックアップファイルの整合性を確認
  - バックアップからの復元テスト（可能な場合）

## 🔄 ロールバック手順

### Phase 1: サービス停止

#### 1-1. ユーザーへの通知

```bash
# システムポータルにメンテナンスモード表示（オプション）
# 現時点では未実装のため、手動でユーザーに通知
```

#### 1-2. FastAPIサーバー停止

```bash
# 方法1: プロセスIDで停止
ps aux | grep uvicorn
kill <PID>

# 方法2: pkillで停止
pkill -f "uvicorn app.main:app"

# 停止確認
curl http://localhost:8000/api/sys/health
# 期待: Connection refused（サーバーが停止）
```

---

### Phase 2: データバックアップ（現状保存）

ロールバック前に、現在の状態をバックアップします（問題調査のため）。

```bash
# タイムスタンプ付きバックアップディレクトリ作成
BACKUP_DIR="/backup/rollback-$(date +%Y%m%d-%H%M%S)"
mkdir -p $BACKUP_DIR

# データファイルバックアップ
cp -r project/backend/data/ $BACKUP_DIR/data/

# アプリデータバックアップ
cp -r project/apps/*/backend/data/ $BACKUP_DIR/apps/

# ログファイルバックアップ（存在する場合）
cp -r logs/ $BACKUP_DIR/logs/

echo "Backup completed: $BACKUP_DIR"
```

---

### Phase 3: 旧バージョン復元

#### 3-1. Gitリポジトリから旧バージョンをチェックアウト

```bash
cd /path/to/websys

# 現在のブランチ・コミットを記録
git log -1 > $BACKUP_DIR/git-current-commit.txt

# 安全な旧バージョンにロールバック
# 例: 前回のリリースタグ
git checkout v0.9.0

# または: 特定のコミットハッシュ
# git checkout <commit-hash>
```

#### 3-2. Python環境の復元

```bash
cd project/backend

# 仮想環境を再作成（念のため）
rm -rf venv
python -m venv venv
source venv/bin/activate

# 旧バージョンの依存パッケージをインストール
pip install -r requirements.txt

# インストール確認
pip list
```

#### 3-3. フロントエンドの再ビルド

```bash
cd project/frontend

# node_modulesを再インストール（念のため）
rm -rf node_modules package-lock.json
npm install

# ビルド
npm run build

# ビルド成果物確認
ls -la dist/
```

---

### Phase 4: データ復元

#### 4-1. 復元方法の選択

**オプションA: バックアップからデータ全体を復元**（データ損失なし）

```bash
# 最新のバックアップからデータを復元
RESTORE_DIR="/backup/pre-deploy-20260602"
cp -r $RESTORE_DIR/data/* project/backend/data/
cp -r $RESTORE_DIR/apps/* project/apps/
```

**オプションB: 一部のデータのみ復元**（問題のないデータは保持）

```bash
# 例: users.json のみ復元
cp $RESTORE_DIR/data/users.json project/backend/data/users.json

# 例: sessions/ のみクリア（セッション再作成）
rm -rf project/backend/data/sessions/*
```

**オプションC: データを保持**（コードのみロールバック）

```bash
# データファイルはそのまま使用
# 旧バージョンのコードと互換性があることを確認
```

#### 4-2. データ整合性チェック

```bash
# users.json のJSON形式確認
python -m json.tool project/backend/data/users.json

# apps.json のJSON形式確認
python -m json.tool project/backend/data/apps.json

# パーミッション確認
chmod -R 755 project/backend/data/
```

### Phase 5: サーバー再起動

```bash
cd project/backend

# 本番モードで起動

```

## 📊 ロールバック判定基準

| 判定 | 条件 | アクション |
|------|------|----------|
| **成功** | ヘルスチェックPASS + 主要機能正常動作 + エラーログなし | 監視継続、v1.1の修正版準備 |
| **部分成功** | ヘルスチェックPASS + 一部機能不具合 | 不具合機能を無効化、監視継続 |
| **失敗** | ヘルスチェック失敗 / 起動しない | 前々バージョンに再ロールバック |

## 🔧 ロールバック後の対応

### 1. 根本原因の調査

- [ ] **問題の原因を特定**
  - ログファイルの詳細分析
  - バックアップデータとの差分確認
  - コードレビュー

- [ ] **再現手順の確立**
  - ステージング環境で問題を再現
  - 修正方針の検討

### 2. 修正版の準備

- [ ] **Issue登録**（`issues/issues.json`）
  - 問題の詳細を記録
  - 優先度: Critical
  - 影響範囲を明記

- [ ] **修正版開発**
  - v1.0.1 または v1.1 として修正
  - ステージング環境で十分にテスト

- [ ] **修正版のリリース計画**
  - テスト完了後、再度デプロイ

### 3. ポストモーテム（事後分析）

- [ ] **問題の振り返り**
  - なぜ問題が発生したか
  - なぜ事前に検出できなかったか
  - テスト不足だった箇所はどこか

- [ ] **プロセス改善**
  - テスト項目の追加
  - デプロイ前チェックリストの見直し
  - 監視体制の強化
